# LarryToday 交叉验证方法

目标是让每项具体主张可追溯、可反驳、可更新，而不是用媒体数量替代证据。目录只能提供核验条件，不能保证未来每一条新闻都得到证实。

## 1. 将报道拆成可验证主张

一篇新闻可能包含“某机构发布了公告”“公告声称发生某事”“某事造成某数量损失”“某政策将产生某结果”。四者需要不同材料；公告只能直接证明前两项，不能自动证明后三项成立。

建议为每项主张记录：

```json
{
  "claim_id": "示例ID",
  "claim_text": "某公司发布了某模型版本",
  "event_time": null,
  "as_of": null,
  "status": "unverified",
  "evidence": [{
    "source_id": "deepseek",
    "document_url": "填写具体原始公告或仓库版本URL",
    "upstream_document_id": null,
    "publisher_family": null,
    "evidence_chain_id": null,
    "relationship": "supports",
    "evidence_type": "first_party_release",
    "direct_observation": false,
    "limitations": "只能确认发布声明；不能证明性能领先"
  }],
  "unresolved_conflicts": [],
  "reviewed_by": null
}
```

这是未来数据结构示例，不是真实新闻或已核验事件。`relationship` 可以是supports、contradicts、context；`status` 可采用unverified、corroborated、disputed、corrected、superseded。`corroborated` 指当前证据支持，不承诺永不修订。

## 2. 独立性按证据链判断

| 组合 | 应如何计数 |
|---|---|
| Reuters原稿＋多个门户转载 | 一条报道链 |
| 公司博客＋媒体复述博客＋该公司高管X帖 | 通常一条公司声明链 |
| BLS数据＋FRED相同序列＋引用该序列的图表 | 一份原始统计；展示方式不是新测量 |
| 同一视频被不同账号转载 | 一个视觉材料；先找最早版本和拍摄来源 |
| ICIJ/OCCRP合作媒体共同发布调查 | 检查共享文档与采访，不能按媒体家数直接累加 |
| 两家记者各自现场采访、不同证人和文档 | 可能独立，但仍需检查是否采访同一人或引用共同匿名来源 |
| 两个冲突方分别发布相互矛盾声明 | 两方立场，不构成事实已证实 |
| 一份法院判决原文 | 可足够确认“法院作出何种判决”；媒体转载不是必要的第二份法律事实 |

用 `publisher_family` 提醒共同机构，用 `upstream_document_id` 和 `evidence_chain_id` 跟踪共同证据。不同母公司也可能共享同一匿名官员或通讯社稿；同集团的不同记者也可能有各自证据。不能仅按域名或集团标签机械判定。

本轮 `publisher_family_hint` 非完整所有权调查，null表示未知而非独立。若需要所有权、资助或编辑立场标签，应记录当前About/Transparency/年报依据及日期，不赋予无出处的左右派评分。

## 3. 按主题组合来源

机器可读组合见 [verification-recipes.json](verification-recipes.json)。其中所有ID均可在 `sources.json` 找到。它们是候选工具箱，不是默认相互独立的背书列表。

| 主题 | 推荐材料组合 | 最容易犯的错误 |
|---|---|---|
| 国际外交 | 正式声明/原视频＋通讯社直接采访＋当地媒体 | 将“声称”改写成“已经发生” |
| 冲突与伤亡 | 各方原声明＋当地现场材料＋救援/调查机构方法说明 | 时间截止、平民定义和失踪人口口径混用；平均冲突数字 |
| AI新模型 | 官方报告/权重/代码＋论文和版本＋外部复现或评测＋产业报道 | 自报分数、第三方转述、排行榜被当作三次独立测试 |
| 网络安全 | 厂商修复说明＋CVE/KEV＋独立研究或受害者证据 | 漏洞存在被写成已经全面遭入侵 |
| 宏观经济 | 统计局原表＋发布日历/修订说明＋财经报道 | FRED与其底层统计重复算来源；同比环比和季调混淆 |
| 公司业绩与投资 | 交易所/监管披露＋财报附注＋直接采写财经报道 | 新闻稿、IR演示和同一份申报当作三个来源；把预测当事实 |
| 监管与法律 | 正式法规/法院文书＋生效日期＋专业报道 | 草案等于法律、指控等于定罪、临时裁定等于终局判决 |
| 医药健康 | 注册记录＋研究原文/系统综述＋监管结论＋专业报道 | 预印本和公司新闻稿变成临床定论；相对风险替代绝对风险 |
| 气候与能源 | 原始观测/统计＋方法和基准期＋地区报道 | 多个机构同用一套观测误当独立；预测替代实测 |
| 灾害 | 官方传感器/预警＋当地应急机构＋现场报道 | 初始震级固定不更新；风险预报当成已发生损失 |
| 社会民调 | 原问卷、样本及加权＋独立统计＋当地采访 | 线上投票当总体民意；不同问题的调查直接比较 |
| 体育文化 | 赛事/奖项/机构原公告＋专业媒体 | 传闻转会当官宣；企业所属媒体与关联消息同源 |

## 4. 有冲突时的发布处理

1. 对齐事件、地点、时间窗口、对象定义、单位和版本，先排除“看似矛盾、口径不同”。
2. 回到最近原始文书或直接观察，确认有没有撤稿、修正、旧图新用或误译。
3. 对照每项主张的支持与反证，不以媒体名气或数量投票。官方说法也可以被证据反驳；立场相反不代表证据同等强。
4. 仍无法解决时，明确归属：“A称……；B称……；截至某时尚无独立材料确认。” 不生成一个折中的数字。
5. 影响重大的战争、健康、市场、犯罪等主张进入人工复核；证据不足就延迟确认或标记待核实。
6. 后续证据改变结论时，保留旧版本、更正时间、原因和新证据。标题、摘要、图表同步更新。

建议日常看板至少显示：独立证据链数量、一手材料比例、本地采写比例、单一集团集中度、待核实主张数量、更正延迟。不要把这些合成为一个貌似精确的“真相分数”。

## 5. 图像、视频、社交内容

从既有X名单、YouTube、bilibili、Reddit或论坛发现线索后，保存原帖ID、发布时间、账号身份依据、最早上传版本和具体地点线索。反向搜图、关键帧、天气/地形比对及历史存档应相互补充。AI生成内容检测器的单一概率不能作为伪造或真实的定论。

个人专家可以解释一个领域，不因知名度就对其所有转述赋予权威。人物账号是声明来源，不能与转述同一账号的媒体算两条证据链。

## 6. 可核对的文档依据

- [SEC EDGAR API](https://www.sec.gov/search-filings/edgar-application-programming-interfaces)：核对披露与XBRL接口，应用时关联具体申报文件。
- [FRED API](https://fred.stlouisfed.org/docs/api/fred/)：包含series、sources及修订日期相关入口；不要丢弃底层来源。
- [arXiv API手册](https://info.arxiv.org/help/api/user-manual.html)：以论文标识和版本追踪研究线索。
- [ReliefWeb API文档](https://apidoc.reliefweb.int/)：聚合的报告应继续关联实际发布机构。
- [USGS GeoJSON](https://earthquake.usgs.gov/earthquakes/feed/v1.0/geojson.php)：保留事件ID、时间和更新时间，适合处理修订。

上述文档支持数据接入与溯源设计；本页交叉验证流程是为LarryToday提出的编辑工作建议，不是这些机构对本项目的背书。
